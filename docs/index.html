Storage models

Three ways to store a vector

The vector dimension determines where Postgres stores the data — and that choice drives most of the latency difference you'll see in the benchmark.

🔵

pgvector · inline (384-dim)

vector(384) = 1,544 bytes. Fits inside the 2 KB heap tuple. Read the row, get the vector — no extra fetch.

No TOAST · heap only
🟠

pgvector · TOASTed (1536-dim)

vector(1536) = 6,152 bytes. Exceeds Postgres' ~2 KB threshold — spills to a separate TOAST relation. Every distance computation needs an extra disk fetch.

TOAST · extra fetch per row
🪣

Vector Bucket (S3)

Supabase Vector Buckets store 1536-dim vectors in S3-backed object storage with an ANN index. Network latency replaces disk latency — scales to millions.

Query modes

Three ways to search

The search type determines how much work Postgres does per query — and whether you ever touch the TOAST relation at all.

Exact KNN (sequential scan)

Every row is fetched and its distance to the query vector computed. No index skips any work.

1
Scan all 150,000 rows — the planner reads the entire table in sequence.
2
De-TOAST each 1536-dim vector — for the TOASTed leg, each row pointer must be followed to the TOAST relation. ~1.2 GB of reads per query.
3
Compute L2 distance for every row, keep the top-k.

Look for: the TOASTed 1536-dim leg is ~7× slower than the inline 384-dim leg. The disk attribution panel shows 100% of reads come from the TOAST relation.

Approximate KNN via HNSW

The HNSW index stores its own copy of every vector. The search walks the index graph and never touches the TOAST relation.

1
Enter the HNSW graph at the top layer — a sparse set of long-range connections.
2
Greedy descent through layers, following edges to closer neighbors at each level.
3
TOAST reads → 0. The index stores its own vector copies — the heap's TOAST relation is never read during search. The disk cost doesn't vanish though: it moves from ~1.2 GB of TOAST pages to the ~800 MB index relation. The difference is the index walk reads only the pages it needs, not all 150k.

Look for: inline and TOASTed legs nearly match (~100 ms vs ~9 s with KNN). The gap narrows but doesn't vanish — the 1536-dim HNSW index is ~800 MB vs ~170 MB for 384-dim, so the graph walk reads more index pages. The disk cost moved from the TOAST relation to the index relation; it didn't disappear.

Hybrid: vector + full-text (RRF)

Two indexes run in parallel and their ranked results are fused with Reciprocal Rank Fusion.

1
HNSW vector search — top-k×10 candidates by L2 distance, ranked 1…N.
2
GIN full-text search — top-k×10 candidates matching the keyword query, ranked 1…N by ts_rank.
3
RRF fusion — score = 1/(60+rank_vec) + 1/(60+rank_fts). Documents appearing in both lists score from both terms. Top-k by combined score returned.

Two architectures: the inline hybrid does this in a single SQL CTE (one round-trip). The bucket hybrid fans out to S3 ANN + Postgres GIN in parallel and fuses in TypeScript (two round-trips).
